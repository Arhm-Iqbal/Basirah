# Basirah

Community security infrastructure for Canadian mosques. Incident reporting, verified alert
fan-out, open-source threat monitoring, facility hardening assessments, and reporting that
feeds Security Infrastructure Program (SIP) grant applications.

Modelled on what SCN and CST provide the Jewish community, adapted for Canada.

---

## Repo layout and ownership

```
frontend/   Next.js app             -> FRONTEND TEAM
backend/    Hono API on Cloudflare  -> BACKEND TEAM
shared/     zod schemas + types     -> BACKEND TEAM (frontend imports, never edits)
supabase/   migrations + RLS        -> BACKEND TEAM
```

**Only edit files inside the folder your team owns.** This is what keeps merges clean. If you
need something changed outside your folder, ask — do not edit it.

This is a skeleton. Every folder is intentionally close to empty.

## Setup

Requires Node 22.

```bash
npm i -g pnpm
pnpm install
```

There is one env template at the repo root. Copy the section you need:

```bash
cp .env.example frontend/.env.local   # keep the NEXT_PUBLIC_ block
cp .env.example backend/.dev.vars     # keep the backend block
```

Frontend on http://localhost:3000:

```bash
pnpm dev:frontend
```

Backend on http://localhost:8787:

```bash
pnpm dev:backend
```

## Stack

This is the approved dependency list. Installing something from it needs no discussion.
Anything not on it does. Most are not installed yet — add them as the work needs them.

**frontend/**

- Next.js 15 App Router, TypeScript strict
- Tailwind CSS v4 + shadcn/ui
- TanStack Query v5 for server state
- `@supabase/ssr` for auth session, `supabase-js` realtime for the live incident feed
- MapLibre GL JS, OpenFreeMap tiles (no API key)
- next-intl for en / fr / ar, RTL via Tailwind logical properties
- Serwist for PWA install and web-push
- lucide-react, date-fns, Recharts 3

**backend/**

- Hono + TypeScript, `@hono/zod-validator`
- Cloudflare Workers via Wrangler 4
- `@supabase/supabase-js` with the service role key
- `@anthropic-ai/sdk` — `claude-haiku-4-5` for volume triage, `claude-opus-5` for flagged items
- Workers KV for rate limits and dedupe hashes only, never PII
- Cron Triggers for ingestion and digests

**supabase/**

- Postgres in `ca-central-1` (Toronto) for Canadian data residency
- PostGIS for geofencing, pgvector for signal dedupe
- RLS deny-by-default on every table

**Hosting:** `frontend/` on Vercel, `backend/` on Cloudflare Workers. Hono is portable, so the
API can move to Vercel unchanged if needed.

## The frontend/backend contract

`shared/` holds the zod schemas for every request and response body. Both sides import from
`@basirah/shared`. It is the single source of truth for the API shape.

- **snake_case in all JSON payloads.** Matches Postgres. No mapping layer anywhere.
- All routes under `/v1/`, plural resource nouns: `/v1/incidents`, `/v1/mosques/:id/assessments`
- IDs are UUIDs, generated by Postgres
- Timestamps are `timestamptz`, serialized as ISO 8601, always UTC
- Errors always return `{ "error": { "code": string, "message": string, "details"?: unknown } }`
- Lists are cursor-paginated: `{ "data": [...], "next_cursor": string | null }`

---

## Security rules

- The **service role key never leaves `backend/`**. The frontend only ever holds the anon key.
- Anything prefixed `NEXT_PUBLIC_` ships to the browser. Never put a secret behind that prefix.
- Every table is RLS deny-by-default. If the frontend cannot read something, the fix is a policy
  or an endpoint, never a key.
- Auth and user-scoped reads go direct to Supabase. Every write with trust implications —
  incident submission, verification, alert fan-out, moderation, report generation — goes through
  `backend/`.

## Ethical constraints

Suspicious-activity reporting has a documented history of being turned against Muslim
communities. These are part of the product, not a disclaimer, and belong in schema and RLS
rather than convention.

- **Behaviour, not identity.** Report forms carry no race, ethnicity, religion, or clothing
  fields. UI copy asks what a person did, never what they looked like.
- **Verification gates broadcast.** No unverified report reaches a community-wide alert.
- **Unverified reports auto-expire** on a scheduled job.
- **Monitoring is inbound only.** Public sources, threats aimed at the community, hashed author
  handles. No dossiers on individuals.
- **Anonymous tips are genuinely anonymous.** Separate table, separate write path, no `user_id`
  column exists, no IP logging.
- PIPEDA and Quebec Law 25 apply. Collect the minimum, state the purpose, keep it in Canada.

## Data model

Planned tables: `profiles`, `communities`, `mosques`, `memberships` (member / mosque_admin /
security_officer / regional_coordinator), `incidents`, `incident_media`,
`incident_verifications`, `alerts`, `alert_deliveries`, `tips`, `threat_signals`,
`signal_scores`, `watchlists`, `facility_assessments`, `reports`, `audit_log`.

Incident lifecycle:

```
submitted -> triaged -> verified -> alerted -> resolved
                     \-> false_alarm
```

Incident categories follow Statistics Canada hate-crime classifications so generated reports
can be benchmarked against the national baseline.

## Code conventions

- No explanatory comments. Comment only non-obvious constraints the code cannot express.
- Prettier config is committed. Do not reformat files you did not write.
- Never commit a `.env`, `.env.local`, or `.dev.vars` file.
- Do not hand-edit `pnpm-lock.yaml`. On conflict:
  `git checkout --theirs pnpm-lock.yaml && pnpm install`.
- Branch naming: `frontend/<feature>` or `backend/<feature>`.
- `pnpm typecheck` must pass before merge. This is the only required gate.
